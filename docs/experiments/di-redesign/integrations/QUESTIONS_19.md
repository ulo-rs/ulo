# Questions after the Q17 and Q18 rulings are built and checked (for the designer)

Written for: the designer. Every ruling in the responses to `QUESTIONS_17` and `QUESTIONS_18` is built, checked by a second model and committed, except the items below that stopped on a decision. The workspace gate runs 2,718 tests with no failure; the examples are 41 packages. Cite these as Q19-P1 onwards. Detail: `FRAMEWORK_GAPS.md` F496 to F503, F345 and the S-item entries.

Paste alongside: core `DESIGN.md` §3.8, §3.9, §9.5; transports `DESIGN.md` §4.3, §5.2, §5.3; the two earlier question files are not repeated here.

## Gates the merge

**Q19-P1. The `abandoned` count (F500 #2).** Reproduced on Linux at about 1 in 3,000 idle runs (6 in 25,300; none in 7,000 under load) in `ulo-rpc-tcp` `conformance_tls`, with `abandoned` 2 where the test expects 1. Cause, traced: `Fixture::start_capped` calls `ready()`, an RPC call; in `Call::run` (`ulo-rpc/src/dispatch.rs` ~359 to 371) `answer(..).await` writes the reply and `drop(exec)` is the last statement, so the client can read the answer, start the held call and the capped close before the server task has dropped its `Execution`; `LiveSet::cancel_all` counts every execution not yet ended. No execution leaks. A user's shutdown report can therefore count a call whose answer was already written. Options: (a) mark the execution ended at the answer; (b) keep the framework and wait in the test. Built: (b), with a deterministic harness test (without the wait it fails at `drain.rs:182`, left 2, right 1) and one sentence in §9.5 step 4. Option (a) was judged unsound: `answer` still uses the execution (`render`, `send`, `stream_reply`), so it needs a second end state in every transport and still leaves a window unless the mark precedes the write. Confirm (b)? Recommendation: yes.

**Q19-P2. The connect bound (Q17-P3 part (ii)).** The ruling's premise, "every link's first connect sits under the same connect bound", does not hold: no RPC link has one. NATS leaves 5 s to async-nats, MQTT 5 s to rumqttc, Redis 1 s to the redis crate, Kafka to librdkafka; none is configurable through ulo. RabbitMQ's refused first connect now fails `listen` as `Bind` in milliseconds (plain connect, close, then the recovering connect). A broker that accepts TCP and never answers the AMQP handshake still holds `listen` and the client's first connect, and lapin cannot be cancelled: a caller-side timeout fires at the bound, but dropping the future leaves lapin's `lapin-io-loop` thread and its socket (probed: the peer saw no close 30 s later), and a broker lost between the two connects hangs the second on the 16-retry backoff. Decisions: (1) the length; (2) whether it is a knob and its name (`ulo-db` and `ulo-ws-redis` use `connect_within`, 30 s); (3) what the expiry carries as its source on a silent listener, where no connection error exists; (4) whether "every link" reaches NATS, MQTT and Redis; (5) whether the leaked thread is a documented limit of the pinned lapin. Recommendation: `connect_within(Bound)`, 30 s, on RabbitMQ only, with the other links' library defaults documented; a named `ConnectTimedOut` source; the leak documented in §5.2 as a measured limit of lapin 4.12, with no upstream request filed.

**Q19-P3. The first-page READMEs.** The root `README.md` and `crates/ulo/README.md` (the crates.io readme) show master's API (`UloFactory`, `AxumAdapter`, `use_http_adapter`, `#[controller]`, `#[inject]`); none of it exists on this branch, and README `rust` blocks compile nowhere. Rewrite before the merge or in the docs-site pass? Recommendation: before the merge, from examples 01, 15 and 39, with the first example compiled as a doctest.

## Rulings needed

**Q19-P4. gRPC hand-written handlers.** The method marker and the spec both name the path and the shape, and DESIGN does not say which the server reads. Proposed (option B): `GrpcHandler::new::<M, _, _>(call).spec(name)`, with `prepare` refusing a spec whose route or shape disagrees with the marker. The checker found the dispatcher never reads the shape at runtime (the extractor decides decoding, the reply decides encoding), so a wrong shape misreports `HandlerInfo` only. DESIGN §0.2 names gRPC as the one exception until this is built. Recommendation: B.

**Q19-P5. `into PreDispatch` is a silent no-op.** `PreDispatch` is module metadata; `into PreDispatch: [value = ..]` compiles and does nothing (probed: `GET /admin/panel` without a key answered 200 where the hand-written module answers 401). Options: build the proposed slot, `meta = [ PreDispatch: |stage| stage.layer(..).apply_for::<ApiKey>([..]).exclude([..]) ]`, or make `into PreDispatch` a compile error pointing at `ModuleDef`. Recommendation: the compile error now; the slot when a second user needs it.

**Q19-P6. `@` on a closure binding.** `with = c @ Q` is refused because `ProviderScope::{bind, try_bind, bind_as, try_bind_as}` return `()`, not a handle `.qualified` can attach to. Return the handle, or keep the refusal (its text tells the user to bind a value or write a `ModuleDef`)? Recommendation: keep the refusal.

**Q19-P7. `ConnectError::Readiness` names no module.** `ConnectError::Hook` now names `StoreModule<S> @ Q`; `Readiness` still carries the unqualified client binding, so two keyed pools fail with identical text. Add the owning module identity to the variant, or print the qualified export key? Recommendation: the owning module identity, as `Hook` does.

**Q19-P8. Naming the link in a `Configure` report (Q17-P1).** "Forward `NoIoDriver` unchanged" and "assert the link named" cannot both hold: `ulo_rpc::Server::prepare` flattens the link's error to text through `Failures::push_error`, and the report prints `transport `Rpc`: <text>`. Built: unchanged, with the `UnusableLink` tests asserting the link. TCP's text no longer says "the TCP link's". Options: the link wraps the error, or `Failures` carries `L::NAME`. Recommendation: `Failures` carries `L::NAME`.

**Q19-P9. A panicking serve future.** Err and early-Ok are handled and pinned (`ulo-runtime-tokio/tests/app.rs`); a panic unwinds out of `App<Bound>::serve` (`app/mod.rs:498` to `559`) with no drain and no close. The smallest fix is a `catch_unwind` per serve poll, converted with `redact_panic` as `prepare` does at `mod.rs:386` to `397`, plus one test. Recommendation: treat it as a transport failure.

**Q19-P10. A panicking instance `Drop`.** A panic inside `release()` leaves the remaining instances undropped (hashbrown stops its drop loop; probed, 1 of 4 undropped). HEAD behaves the same. Accept and document, or catch and continue? Recommendation: document it.

**Q19-P11. The config report's limits.** After the Q18-P5 fix every section is read separately. Documented, not closable in general (serde's derive stops at the first missing field in declaration order, and the leaf types that fail also refuse a placeholder): a section written under a `#[serde(alias)]` key that ends on a leaf error is also reported as "missing required field" under the real name (HEAD reported one problem); a missing section whose type refuses a placeholder hides missing fields declared after it; the fields of a flattened struct after a failed section are not reported. The pass cap (`MAX_PASSES`) truncates a root map of 3,000 failing entries to 2,048 in 9.6 s (debug) without saying so. Accept the wording, and make the cap say it truncated? Recommendation: yes to both.

## Confirmations

**Q19-P12. SPI changes made to wait for the subscription (Q18-P4).** `BroadcastAdapter::subscribe(&self, node, timer: Arc<dyn Timer>)` returns a future of `Result<stream, BoxError>`; `Hub::start` and `GatewayTable::start` are async and fallible; `UpgradeHandler::bound` is async and fallible, awaited by `Server::bind` (which closes its backend on error), and `Embedded::bind` installs its service only after it succeeds. The wait runs on the app's `Timer` through `ulo::timeout`, so an adapter runtime without the time driver no longer panics `listen`. `Redis::connect_within(d)` defaults to 30 s (the builder's choice; the ruling said "the link's connect bound"; see P2). Confirm the SPI and the default.

**Q19-P13. Public surface added.**
- `ModuleIdentity::of_owner` went from `pub(crate)` to `pub` (a module can have a module type other than its config type); `of_type::<O>().configured(&c)` would compose with `label`.
- `ulo::UndeclaredRead { reader(), key() }`, wrapped in `Permanent`.
- The handler API names the builder chose: `HttpHandler::new(method, call).reads_path::<T>().reads_host::<T>()`, `RpcHandler::message` and `event` with `.payload(PayloadKind)`, `WsHandler::new(call)`, `GatewayHooks::<G>::new().on_connect().on_disconnect().after_init().mount(m)`, `WsCx::reply` and `reply_stream` (which require `T: 'static`; `RpcCx::reply` does not), and extension number X40.
- `Tls::from_config` lives in `ulo-net`. It refuses a config missing a protocol the transport needs: http/1.1-only (named in the ruling), h2-only (not named; an h2-only list leaves HTTP/1.1 clients unable to negotiate), and an unknown protocol only. It keeps extra protocols after the server's, so a config shared with HTTP makes gRPC offer `[h2, http/1.1]` and WS `[http/1.1, h2]`; a client offering only the extra protocol fails after the handshake instead of receiving a TLS alert. Trim the list to what each transport speaks?
- `ulo_rpc`'s root cannot re-export `Link` (it collides with the `Link` trait): rename it, or place it in a module?

Recommendation: accept all; trim the extras; re-export `Link` under a module.

**Q19-P14. The undeclared-read check (Q18-P3).** On in every build, as ruled. It also checks extension reads and `ExecutionRef` reads (an undeclared one escapes the needs-execution scope check); `r.module()` is not checked (it returns a `ModuleRef`, and the ruling treats `ModuleRef` use as a call-time read). A `ModuleRef` or `ExecutionRef` used inside `construct` also reads freely, and declaring `Ext<A>` covers a read of `Ext<B>`; the docs now say both. Cost, release, 10 alternating pairs at load 3: the check itself about +12 ns per construction (+3%, inside the 20 ns bar); the tree as a whole +35 ns (+9.5%) over HEAD, of which about 25 ns appears with the check off and is unlocated, most likely the execution-end change. Bisect, or accept? Recommendation: accept.

**Q19-P15. Rulings of Q18 that the code or a probe contradicted.**
- Q18-P11 H5: "a request arriving in that moment is still served" is false. `drain()` sets the Draining phase before it fires `draining`, and `AppShared::open` refuses ordinary executions from Draining on (probed: refused 60 of 60; a request head on an earlier connection answered 503 30 of 30; a fresh connect refused 60 of 60; never 200). `phases.rs`, the HTTP conformance drain case and §9.5 step 3 already say so. The docs now say `draining()` resolves once the phase is Draining, new executions are refused from then, and the listeners stop accepting a moment later. Confirm that the code and §9.5 were right.
- Q18-P1: after an execution ends, every read through its handle or its resolver refuses with `ExecutionEnded`, the cache is released, extensions stay readable, and `CallError::from_boxed` maps it to `Internal`. Usability consequence: a subscription stream built from `exec.handle()` inside `app.execute(..)` and returned out of the closure now fails at its first read with outcome `Failed`. The `Execution` docs on `execute` should say the stream must be consumed inside the closure. Add the sentence?

**Q19-P16. A connect guard and the session (G25).** A connect guard's extensions reach `on_connect` only; each message is its own execution (`ulo-ws-hyper/tests/execution_scope.rs`). A guard can write the session, but a field written after the session is built needs interior mutability, which example 23 shows with a `OnceLock`. Should a connect guard be able to seed the session (the guard returns a value the session is built from)? A convenience question; recommendation: no, until a second example needs it.

**Q19-P17. A handler declared Unary that returns `reply_stream`** still streams: a unary caller gets `Internal` "unexpected `item` frame", `HandlerInfo` says Unary, and the link was checked against Unary. Documented. Refuse instead? The shape cannot be read statically from the call. Recommendation: leave it documented.
