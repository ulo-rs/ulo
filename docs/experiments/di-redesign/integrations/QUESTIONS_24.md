## Rulings needed

**Q24-P1. `migrate` cannot be compared by what the migrator is (Q23-P8, F574).** `StoreModule::migrate` takes an owned `impl Migrations<S>` and erases it. `ulo-db-sqlx` implements `Migrations` for an owned `Migrator`, not for `&'static Migrator`, so the address comparison the ruling names has no value to compare. SeaORM's `SeaOrmMigrations<M>` is a zero-sized type that could compare by `TypeId`, but `.migrate` cannot tell it from sqlx's single `Migrator` type without a hook on the trait. Diesel's `DieselMigrations<M>` holds a value, and `embed_migrations!()` is usually a `const` with no stable address. The checker's smallest design: a provided `fn identity(&self) -> Option<MigratorIdentity>` on `Migrations` (`MigratorIdentity::of_static(&'static T)` and `of_type::<T>()`), `impl Migrations<S> for &'static Migrator` in `ulo-db-sqlx` keyed by address, `of_type::<M>()` on `SeaOrmMigrations<M>`, and Diesel on the call site. The documented way to write a shared sqlx migrator becomes `static MIGRATOR: Migrator = sqlx::migrate!();` passed as `&MIGRATOR`, because an inline `&sqlx::migrate!()` gets its own address at each occurrence. Options: build that design; or keep the call-site comparison and document its false refusal and false match. The ledger holds it unbuilt. Recommendation: build it.

**Q24-P2. Settings outside the identity that still go first-reached-wins (Q23-P1, F575).** `WsModule`'s gateway defaults (`message_limit`, `max_connections`, `max_inflight`, `server_max_inflight`, `max_outbound`, `ping_interval`, `pong_timeout`) and `OtelOptions`' `service_name`, `sample_ratio` and `flush_timeout_ms` are plain comparable values, unlike the exporter and adapter. The ruling named only kind, endpoint, protocol and URL, so a second registration with other values of these still resolves silently, which is the behaviour QS-14 removed. The checker wrote a patch that compares them; it is not applied. Options: compare them; or state in the module docs that they are not settings and the first registration wins. Recommendation: compare them.

**Q24-P3. `%5C` and the dot-segment 400 carry no CORS headers (Q22-P3, Q22-P5, F576).** Q22-P5 accepted the dot-segment 400 without CORS headers because "no browser sends it". That premise fails for `%5C`: a browser keeps percent-escapes, so a cross-origin page that sends `encodeURIComponent("\\")` sees a CORS failure instead of the 400. The refusal comes before every entry, which also keeps the path from an unscoped static-file layer. Separately, under `Miss::Forward` the 400 pre-empts a host route: on rocket the host route `/files/<name>` answers `/files/plain` with 200 and `/files/a%5Cb` with ulo's 400. Dot segments have done the same since QS-3. Q22-P5 ruled that ulo must not speak for routes it does not own. Options: leave the order and document both; or refuse in the router and leave the 400 to requests ulo routes, so a forwarded host path is untouched and a routed one has its CORS headers; or both: forward untouched, refuse routed requests after the unscoped entries. Recommendation: the third.

## Confirmations

**Q24-P4. The reachability reading of the exclusion check (Q22-P2).** The ruling's example, a static route claiming only `GET` so that `POST /admin/health` still reaches `/admin/{page}`, does not occur in this router. §3.2 has the most specific matching pattern decide the method, so `POST /admin/health` answers 405 at the static route and never reaches the pattern route. A higher-precedence route therefore claims its paths for every method, and the check ignores the method. The refusal stands where no higher-precedence route exists for the excluded path. Confirm the method-agnostic check.

**Q24-P5. `\` is refused over the whole path (Q22-P3).** The builder and checker read the ruling's two rules as one refusal at the same point as a dot segment, before pre-dispatch and routing: a raw `\`, `%5C` or `%5c` anywhere in the path answers 400, covering every `{name}` and `{*rest}` value. `%255C` reaches the handler as the text `%5C`. The cost is that a static route segment containing `\` or `%5C` is accepted at registration and can never match, and that an unrouted path with one answers 400 rather than 404. Confirm.

**Q24-P6. How far the `grpc-` reply screen reaches (Q23-P2).** The screen drops a `grpc-` name an interceptor adds after the snapshot, and also writes back a name an interceptor changed or removed, because otherwise an interceptor could rewrite `grpc-status` on a trailers-only reply, which carries it as a header. A `Reply` built by hand rather than through the context carries no record and passes unscreened, because the usual hand-built error reply, `Status::into_http()`, carries `grpc-status` as headers and would lose it. A pre-dispatch entry can still write `grpc-status` onto a 200 reply that carries a message (F579). Confirm the write-back and the hand-built boundary.

**Q24-P7. What a setting's text may carry (Q23-P1, Q23-P8, F580, F581).** Userinfo is stripped from the Redis URL and from the OTLP endpoint, the second beyond the ruling's text. Three remainders: an OTLP endpoint's query string (`?api_key=`) is reported raw; a Redis password in a query parameter (`redis+unix:///sock?pass=..`) is not userinfo, so it prints in the `url` setting and in the error; and a secret declared only by the refused second registration, or by a reloaded module, is never registered with the graph's redactor, because its `register` never runs. The first two want a rule for which URL parts a setting may carry. Options: report only scheme, host and port of an endpoint and URL; or strip userinfo and known credential parameter names. Recommendation: scheme, host and port only. Confirm the OTLP userinfo strip with it.

**Q24-P8. A drive prefix in a path parameter (Q22-P3, F577).** A Windows `Path::join` replaces its root when the joined value carries a drive prefix, so `C:x` escapes the root as `\` does. ulo does not refuse a `:` in a parameter, and the QS-3 docs now say so, because refusing it breaks ordinary values such as `a:b`. Options: document it as the application's check; or refuse a value that starts with a drive prefix (an ASCII letter and `:`) when it is a whole segment. Recommendation: document it.

**Q24-P9. A scope that names only reflection paths (Q22-P1).** The check found that such a scope was refused at `listen()` as matching no route, because the prepare-time check was fed only handler paths. It is now accepted, since the entry runs. A scope naming only the health service's path is still refused with the same text, though health runs no scoped entry; the message says "matches no route's path" and does not say why. Confirm the acceptance, and whether the health message should name the exemption.

## For the record

**Q24-P10. The UDP spent-cap flake (F586, F587, #398).** After #397 merged, `a_call_held_past_a_spent_cap_is_answered_unavailable` failed on the UDP link in CI in two of three runs, the held call meeting its own `Timeout`. The mechanism is the one in F482, F479 and F522: the call's task queues its `unavailable` after the server writer has ended, because `close` returned first. UDP's `close` now forgets and answers every held call in its first poll under the call table's lock, and the reply path looks up, queues and finishes under the same lock. With a 50 ms stall on the worker that renders the reply, the whole binary failed 13 of 100 runs on Linux before and 0 of 100 after. A request that the receive task decodes between the sweep and its abort is still opened in the cleared table (F590); NATS closes that window with a `closed` flag checked on the way in. Three more UDP scenarios flake on HEAD at about 1 to 2 percent (`drain_window`, `over_the_bound`, F588, F589).
